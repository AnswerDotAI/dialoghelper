Channel

def Channel(
    chan, url:NoneType=None
):

Duplex JSON messaging with the other peers on a named /wsx relay channel

Connect each peer to the same channel name on Solveit’s /wsx relay. The relay forwards each frame unchanged to every other peer on that channel. solvecdp uses Channel to communicate with the solveit-chrome extension.

Channel sends JSON dictionaries. Pass the fields as keyword arguments to send. Incoming frames become AttrDict objects. If a frame’s id matches a pending request, it completes that request. Other frames go into the events queue.

Here we connect two peers and send a greeting. The second peer reads it from events.

ch1,ch2 = await Channel.connect('test'),await Channel.connect('test')
await ch1.send(hello='world')
test_eq((await ch2.events.get()).hello, 'world')

request adds a unique id and waits for a reply with that id. Requests can run concurrently. The peer answering a request must include its id in the reply. This example replies with twice the supplied number.

async def _responder():
    msg = await ch2.events.get()
    await ch2.send(id=msg.id, result=msg.x*2)

task = asyncio.create_task(_responder())
test_eq((await ch1.request(x=21)).result, 42)

Check is_open before and after closing the connections.

assert ch1.is_open
await ch1.close()
await ch2.close()
assert not ch1.is_open

realpath() returns the gateway’s on-disk root. realpath('') returns the current notebook’s folder. Other relative paths use that folder, regardless of the kernel’s cwd. Dialog model

Dialog and Message extend aidialog’s classes with Solveit’s metadata fields. meta_attrs maps each attribute to its stored metadata key. Reading a message makes these fields available as attributes. Serializing the message writes them back to metadata.

At startup, a Solveit kernel registers this Dialog class with aidialog.dlgskill.set_dlg(path, cls=Dialog). Subsequent reads through aidialog.dlgskill use these subclasses for the current dialog.

data_root

def data_root():

The data directory dialog names are relative to

The editing tools use the gateway’s cells API. They send batches of operations to add or delete cells, merge metadata, or toggle flags. An edit that needs a message’s existing content reads that cell before sending its replacement.

Writes do not check whether the cell changed since the read. The last write to a field wins, as it did with direct file editing. Solveit updates its view from the gateway’s broadcasts rather than waiting for a file watcher to report a diff.

Gateway kernels have RUSTYGATE_URL in their environment. Set dh_settings['rusty'] to override it during development or tests. cells_client binds a client to one dialog’s notebook under the gateway’s data root. data_root resolves that root for operations that still use filesystem paths.

update_msg follows Message.update for metadata. meta= replaces the metadata dictionary. mergemeta= merges nested dictionaries and deletes keys whose value is None.

A metadata merge on its own uses a gateway merge operation. It follows JSON merge-patch rules, where null deletes a key. A metadata replacement, or a merge combined with content changes, uses the serialized message in an unconditional update operation.

run_code_interactive

async def run_code_interactive(
    code:str, # Code to have user run
):

Insert code into user’s dialog and request for the user to run it. Use other functions where possible, but if they can not find needed information, ALWAYS use this instead of guessing or giving up. IMPORTANT: This tool is TERMINAL - after calling it, you MUST stop all tool usage and wait for user response. Never call additional tools after this one.

Message.execute and Dialog.execute run messages in the current Solveit kernel. They replace aidialog’s default CaptureShell execution, which uses a temporary shell. The Solveit server handles these runs like user-initiated runs, including attribution, the spinner, streamed card updates, and saving to disk. Awaiting execute returns the messages’ outputs.

A tool can call execute while its own message is still running. Adding that work to the main shell’s serial queue would deadlock. execute routes the nested work through the kernel’s persistent sidecar subshell instead. The sidecar runs it on a separate serial queue while the calling message waits.

When py runs with safepyrun’s audit checks, the nested execution remains inside that audit window. execute does not add a separate sandbox.
